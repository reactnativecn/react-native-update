### 优势

1. 对中国用户使用阿里云高速 CDN 分发，对比其他服务器在国外的热更新服务，分发更稳定，更新成功率极高。海外用户智能分流至 cloudflare，同样提供稳定高速的分发体验。
2. 基于 bsdiff/hdiff 算法创建的**超小更新包**，通常版本迭代后在几十至几百 KB 级别（其他全量热更新服务所需流量通常在几十 MB 级别）。整条链路更是**针对 Hermes 字节码做了专门优化**：自 CLI 2.22 起，bundle 以 Hermes **delta 模式**编译使字符串 ID 跨版本稳定、debug info 段被剥离，diff 本身再经过 HBC 感知的变换（详见下方[算法对比](#diff-算法对比)）。新增的两项编译期优化完全在构建侧完成，**已上架的应用只需重新构建一次发版，补丁就会变小**。
3. 始终跟进 RN 最新正式版本，第一时间提供支持。支持 hermes 字节码格式。支持新架构（注：安卓 0.73.0 ~ 0.76.0 的新架构因官方 bug 不支持，0.73 以下或 0.76.1 以上的新架构可用）。
4. 跨越多个版本进行更新时，只需要下载**一个更新包**，不需要逐版本依次更新。
5. 命令行工具 & 网页双端管理，版本发布过程简单便捷，完全可以集成 CI。
6. 后台自带**数据统计**（版本分布、更新成功率等）、**灰度发布**（按比例逐步放量）与**版本健康度监控**，无需自建数据链路即可掌控每次发布。
7. 支持崩溃回滚，安全可靠，结合健康度监控可及时发现并止损问题版本。
8. meta 信息及开放 API，提供更高扩展性。
9. 提供 **MCP 服务**：把热更新服务接进 Claude Desktop、IDE 或自建 Agent，用自然语言排查"这台设备为什么没收到更新"，并可与 GitHub、Sentry、CI 等工具组合定位问题。全程只读、按应用授权（[Pushy 文档](https://pushy.reactnative.cn/docs/mcp) / [Cresc 文档](https://cresc.dev/docs/mcp)）。
10. **原生冷启动自愈**：即使热更版本坏到 JS 完全跑不起来（白屏、启动即崩），设备也能在下次启动时由原生侧自动拉到修复版——不需要用户重装，也不需要你发新的应用商店版本（详见下方[原生冷启动检测](#原生冷启动检测)）。
11. 提供付费的专人技术支持。

### 原生冷启动检测

自 10.52.1 起，每次冷启动后数秒会在后台线程执行一次**不依赖 app bundle** 的更新检查（下载、打补丁与状态切换全部在原生侧完成）。它的存在只为一件事：**当前热更版本坏到 JS 起不来时，仍有一条能把修复版拉下来的通路**——常规更新流程仍由应用内的 JS 负责，检查结果会被 JS 侧复用，不会重复请求。

几个需要知道的点：

- **不阻塞启动**：延迟数秒、跑在后台线程，成果在**下次启动**生效。
- **是否自动激活取决于你的配置**：`updateStrategy` 为 `silentAndNow` / `silentAndLater` 且未关闭自动检查（`checkStrategy` 不为 `null`）时，原生侧才会把下载好的版本设为下次启动生效；其余情况只下载，激活权仍在 JS。
- **救砖指令**：控制台可按版本标记「强制启动」，被标记的版本无视上述策略直接在下次启动生效——这是把已被坏版本卡死的设备捞回来的手段。设备本地的崩溃回滚保护仍然优先，已回滚过的版本不会被再装回去。
- **崩溃时刻救援**（Android 与 iOS）：应用在启动阶段死于未捕获的 JS 错误时，SDK 会短暂扣住垂死的进程（数秒、有硬上限），把检查与下载做完——即使版本每次启动零点几秒就崩，也能被换掉。该窗口内下载到的修复版一律设为下次启动生效（JS 已经没有机会做决策了）。崩溃上报不受影响：SDK 以链式方式保存并在结束后调用原有的崩溃处理器。不覆盖：原生（非 JS）崩溃、ANR、OOM 击杀，以及 iOS 上安装了自定义 `RCTSetFatalHandler` 的应用（那时 React Native 不再抛出本机制拦截的异常）。
- **断点续传**：更新下载在进程死亡后保留进度、下次以 HTTP Range 续传，反复的短命启动也能单调累积进度；紧随中断轮次的下一次启动会跳过延迟立即续传。鸿蒙不需要崩溃时刻扣留：RNOH 下未捕获的 JS 错误不会杀死进程，JS 启动即崩时原生检测照常完成。
- **可以关闭**：`disableNativeCheck: true`。关闭后每次冷启动少一次后台请求，代价是**放弃上述自愈能力**——被坏热更卡死的设备将无法自动恢复。仅在这次请求本身构成问题时（流量/耗电预算、隐私清单申报、需用户同意后才可联网）才建议关闭。

### Diff 算法对比

补丁体积在发布链路的三个独立环节分别被压缩，三层叠加生效。其中第 1、2 项是 **CLI 2.22 新增，且完全在构建侧完成**：它们改变的是喂给 hdiff 的字节码，因此已经上架的应用只要下一次发版用新版 CLI 构建即可受益——不需要升级 SDK，也不需要重新发版。第 3 项需要客户端具备反变换能力（SDK ≥ 10.48）。

| # | 优化 | 作用位置 | 消除的东西 | 起始版本 |
|---|---|---|---|---|
| 1 | Hermes delta 模式（`-base-bytecode`） | hermesc 编译期 | 版本间字符串表重新编号 | **CLI 2.22** |
| 2 | 剥离 debug info（`-output-source-map`） | hermesc 编译期 | 字节码的 debug info 段，实测占 HBC 的 21% | **CLI 2.22** |
| 3 | HBC delta-friendly 变换 | 发布端，hdiff 之前 | 偏移量表的位移放大 | CLI 2.17 |

#### 1. Hermes delta 模式（`-base-bytecode`）——CLI 2.22 新增

Hermes **每次**编译都会按标识符出现频次重排字符串表。JS 改一行，大部分字符串 ID 就会被重新编号，于是两份字节码几乎处处不同——程序其实几乎没变，diff 却被撑爆。

现在 `bundle` 会以同一应用更早的一份字节码为基准编译（`hermesc -base-bytecode=<base.hbc>`），把已有的字符串 ID 钉死在原位，真正进入补丁的只剩真正改动的部分。

在与下方表格同一个应用、同样三个场景上实测（以链根为基准打补丁，每个补丁都经过往返校验，每个 delta 产物都通过与普通编译的等价性校验）：

| 场景 | hdiff | hdiff + HBC 变换 | **delta 模式** + 两者 |
|---|---|---|---|
| 单行文案修改 | 84.6 KB | 62.8 KB | **3.4 KB**（18.5 倍） |
| 小功能（约 60 行） | 319.5 KB | 276.2 KB | **50.2 KB**（5.5 倍） |
| 中等功能（约 300 行） | 414.6 KB | 381.0 KB | **97.8 KB**（3.9 倍） |

单行修复只需下发 **3.4 KB**——比 1.5 MB 的全量包小 455 倍。两项 Hermes 优化互补而非重复：在 delta 模式之上，HBC 变换仍能再减 9%～36%——delta 模式稳住字符串 ID，变换则吸收真正插入代码后残留的偏移位移。

- **默认开启**（`--hermesBase auto`）。base 由更新服务下发（`GET /app/:id/hermesBase`），返回的是**当前字节码链的根**——同一 epoch 内所有版本都以同一份 base 编译，因此设备跨多个版本升级时依然只需下载一个小补丁。链根尚不存在时，服务端依次回退到最新的历史版本、最新的原生包。
- **按内容校验**。base 会核对 sha256，并存入本地缓存（`.pushy/cache/<sha256>`，默认 500 MB / 20 个 LRU；容量上限用 `--cacheMaxMb` 或 `PUSHY_CACHE_MAX_MB` 调整，目录位置用 `PUSHY_CACHE_DIR` 指定，`pushy cache [clean]` 查看或清空）。发布版本、上传 APK/IPA/APP 时都会把刚构建出的 bundle 顺手写进缓存，因此下次发版通常根本不需要下载。
- **按字节码校验**。`--verifyHermesBase`（默认开）会再做一次**不带 base** 的编译，并把两份反汇编以流式方式逐条指令比对。只要出现不一致、hermesc 失败或服务端不可达，一律改用普通编译产物。**这个特性不可能卡住发版，也不可能污染产物。**
- **启用条件**。只有包含上游 delta 模式修复的 hermesc 才会被使用：经典的 `react-native/sdks/hermesc` / `hermes-engine`，或 `hermes-compiler` ≥ 250829098。其余情况，以及 base 的 HBC 版本与当前编译器不匹配时，都回退到普通编译。
- **手动指定 base**。`--hermesBase <file.hbc|.ppk|.apk|.ipa>` 以本地产物为基准编译——通常就是你要打补丁的那个商店包。`--hermesBase none` 关闭该模式。

#### 2. 不再下发 debug info——CLI 2.22 新增

`hermesc` 现在始终带 `-output-source-map` 调用，这会让它把 debug info 段从产出的字节码里剥离——与 React Native 自身的 release 构建做法一致。在评测应用上这一项稳定为**字节码本身小 21%**（4.32 MB → 3.41 MB），全量包和由它派生的每一个补丁都随之变小。

信息并没有丢失：Hermes sourcemap 会写在中间目录里紧挨 bundle 的位置（`.pushy/intermedia/<platform>/<bundle>.map`），且永远不会被打进 ppk。想事后符号化崩溃报告里 `address at …` 形式的堆栈，把这个文件留好即可；传 `--sourcemap` 时它照旧与 packager map 合成。

#### 3. HBC delta-friendly 变换

传统 diff 算法直接对字节做差分，而 Hermes 字节码中大量结构是"偏移量表"——JS 一处小改动会令其后所有偏移量整体位移，导致二进制差异被急剧放大。我们在 hdiff 之前引入了一层**针对 HBC（Hermes 字节码）的 delta-friendly 可逆变换**：对偏移位域做前项差分，从根源上消除这种位移放大。布局描述表由发布端随补丁下发，Hermes 版本演进时**客户端零升级**、自动兼容。

以下数据在真实 RN 0.86 应用的 release 产物上实测（Hermes HBC v98，字节码约 4.4 MB），每个补丁都先通过完整往返校验再记录体积。完整的评测方法、测试数据与可复现代码见 **[hbc-diff-benchmark](https://github.com/sunnylqm/hbc-diff-benchmark)**。

这组数据单独衡量的是第三层：同一对 bundle 走五条不同的 diff 链路。第 1 项优化改变的是 bundle 本身，其收益不体现在这张表里——它与表中数字是相乘关系，而非已被包含在内。

**Hermes 字节码（.hbc）——生产环境 Hermes 应用的实际发包格式：**

| 迭代场景 | 全量 OTA（gzip） | bsdiff | bsdiff+lzma | hdiff | hdiff + HBC 变换 |
|---|---|---|---|---|---|
| 单行文案修改 | 1901.5 KB | 93.7 KB | 87.7 KB | 89.0 KB | **63.5 KB**（−28% / −29%） |
| 小功能（约 60 行） | 1913.9 KB | 411.6 KB | 330.9 KB | 328.0 KB | **285.5 KB**（−14% / −13%） |
| 中等功能（约 300 行） | 1973.7 KB | 551.6 KB | 430.6 KB | 431.6 KB | **398.4 KB**（−7% / −8%） |

**文本 JS bundle——非 Hermes 应用（同一应用、同样三个场景）：**

| 迭代场景 | 全量 OTA（gzip） | bsdiff | bsdiff+lzma | hdiff |
|---|---|---|---|---|
| 单行文案修改 | 807.2 KB | 0.3 KB | 0.7 KB | **0.1 KB** |
| 小功能（约 60 行） | 813.1 KB | 7.4 KB | 7.4 KB | **5.8 KB** |
| 中等功能（约 300 行） | 837.7 KB | 38.4 KB | 37.4 KB | **28.7 KB** |

文本 bundle 没有偏移量表，diff 天然干净——补丁只有几百字节到几十 KB，较大改动下 hdiff 仍比 bsdiff 小约 20%~25%。偏移位移放大是 Hermes 字节码特有的问题，这正是 HBC 变换存在的意义。

要点：

- 增量更新比全量 OTA 节省 **5~30 倍**流量（单行改动 63.5 KB vs 全量 1.9 MB）；再叠加 delta 模式后，这个单行改动只有 3.4 KB。
- bsdiff+lzma 对照组（同一份 bsdiff 差分数据、换用 lzma 压缩）表明压缩器占了 bsdiff 与 hdiff 差距的大头——而 HBC 针对性变换再带来的 **7%~29%** 缩减是**纯算法收益**，且越是高频的小改动收益越大。
- hdiff 生成补丁比 bsdiff 快 **2~4 倍**，变换本身开销仅个位数毫秒。
- 每一层都有安全兜底：改写任何字节前先对段边界、位域范围做全量校验，delta 模式产物要与普通编译结果比对，任一环节不匹配都自动回退到上一层的原有行为。
